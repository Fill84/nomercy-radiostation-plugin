# The catalogue is stuck at 1.0.0, and a correct entry cannot currently be written

**Repo:** `NoMercy-Entertainment/nomercy-plugins`
**Found:** 2026-08-13, against `master` and a live server on `app.nomercy.tv`.
**Raised:** NoMercy-Entertainment/nomercy-plugins#2. Open.

## What happens

Dashboard → Plugins → Catalogue offers *"Internet Radio Provider 1.0.0 — Adds a curated list
of internet radio stations as a music media source"* with an **Install plugin** button, on a
server that already has this plugin running. No update is ever offered.

## Where the catalogue comes from

Not from this repository's releases, and not from the media server. The client asks the
server for `plugins/repositories/available`, and the server reads the repository URLs in
`%LOCALAPPDATA%\NoMercy\plugins\configurations\repositories.json`. On beast-unit that is one
entry:

```json
[{ "Name": "NoMercy Plugins",
   "Url": "https://raw.githubusercontent.com/NoMercy-Entertainment/nomercy-plugins/master/index.json",
   "Enabled": true, "Trusted": false }]
```

That index still carries this plugin's first release, so the catalogue is reporting it
correctly. The `repository.json` this repository publishes with every release since 1.0.2 is
read by nothing.

## Three problems, and only the first is stale content

1. **The entry is from 1.0.0.** Name, description and version all describe a plugin that
   shipped a curated station list — the opposite of what this one does now. 1.0.1, 1.0.2,
   1.1.0 and 1.2.0 have all been released since.

2. **The schema cannot express this plugin's id.** `schema.json` declares
   `"id": { "format": "uuid" }`, and the README states that a server tells an update from a
   different plugin by that id. The server moved plugin identity to `Ulid` (see `8f5aac5`
   here, "move to the server's Ulid plugin identity"), so `plugin.json` now reads
   `5KTKRT4Z2Y9P59Y40W5CX4TQKF`. Listing the real id fails validation; keeping the old GUID
   `b3d4f1a2-…` validates and guarantees the update never lands. There is no third option, so
   adding 1.2.0 under the old GUID would be worse than the stale entry — it would look fixed
   and still never apply.

3. **`downloadUrl` is specified as a bare `.dll`.** This plugin needs `plugin.json`,
   `deps.json` and `lang/` beside its assembly, so it ships a zip — and the existing entry
   already points at one, contradicting the schema's own description.

   Not theoretical: the install on beast-unit contained **only**
   `NoMercy.Plugin.InternetRadio.dll`, with no manifest and no `lang/`, while YouTube and
   TorrentDownloader each had their full set. Every locale silently falls back to English in
   that state, and the server has no manifest on disk to read.

## What this repository already provides

Everything an entry needs, per release, generated by CI from the manifest:

```
.../releases/download/v1.2.0/repository.json
```

carrying version, targetAbi, download URL and a `sha256:` checksum — verified against the
published zip as `248e00eb…1bf920`. If the index could consume a per-plugin repository URL
instead of a copied-out snapshot, entries would stop going stale on every release. That is
the underlying cause rather than anyone forgetting to open a PR.

## Not fixed from here

No PR was sent against `index.json`: points 2 and 3 are decisions for that repository, and
any entry written today would encode a guess about both.
