# The generated manifest schema types `capabilities` as an array; the runtime binds it to an object

**Repo:** `nomercy-media-server` (the generated `PluginManifestSchema` and the `PluginManifest`
type it is supposed to describe)
**Found:** 2026-09-23, against `dev` at `4c16c0d09f4bcc2fa3a39ad2e791f52441cdd69b` (fetched
today; unchanged from the commit the 2026-09-22 audits read).
**Raised:** not yet. `gh issue list -R NoMercy-Entertainment/nomercy-media-server --state all
--search "PluginManifestSchema" / "capabilities array" / "manifest schema entry"` — no
results.

## What happens

`PluginManifestSchema.Json` is a generated JSON Schema, shipped as a public constant in the
SDK abstractions package (`src/NoMercy.PluginSdk.Abstractions/Generated/PluginManifestSchema.cs`,
header: "Generated by tools/plugin-contract. Do not edit."). It requires `entry` at the top
level and types `capabilities` as an array of `{name, scope, reason}` objects:

```json
// PluginManifestSchema.cs:25-33 (required)
"required": ["id", "name", "description", "version", "targetAbi", "assembly", "entry"],
```
```json
// PluginManifestSchema.cs:93-98 (capabilities)
"capabilities": {
  "type": "array",
  "items": { "$ref": "#/$defs/capabilityGrant" }
},
```
```json
// PluginManifestSchema.cs:119-124, 185-190 ($defs.capabilityGrant)
"capabilityGrant": {
  "type": "object",
  "required": ["name"],
  "additionalProperties": false,
  "properties": {
    "name": { "type": "string", "enum": [ ... ] },
    "scope": { "type": "string" },
    "reason": { "type": "string" }
  }
}
```

The C# type every manifest is actually read into disagrees on both points. `capabilities` is
a single object, not an array:

```csharp
// PluginManifest.cs:69-70
[JsonPropertyName("capabilities")]
public PluginCapabilities? Capabilities { get; init; }
```

`PluginCapabilities` (`PluginCapabilities.cs:16-44`) is a class with `hooks`/`network`/`ui`/
`rest`/`restAnonymous`/`ws` properties — the shape every real manifest in this workspace
uses (this plugin's own `plugin.json`, Automix's, the torrent plugin's, the SDK template's).
None of them carry an array of `{name, scope, reason}` objects anywhere. And `entry`, which
the schema requires, is read by nothing:

```csharp
// PluginManifest.cs:48-49
[JsonPropertyName("entry")]
public string Entry { get; init; } = string.Empty;
```

`grep -rn "\.Entry\b" src/ tools/` finds no read of `manifest.Entry` outside unrelated
matches (`stem.Entry` on an audio-stem record, EF Core's `context.Entry(...)`). The property
exists, defaults to empty, and is required by the schema but optional in the C# type and
consulted nowhere at runtime.

## What actually happens to an author who follows the schema

Not a silent null, and not a failure deferred to "first facade use" — I checked this
empirically rather than assume default `System.Text.Json` behaviour. A manifest whose
`capabilities` is a JSON array (as the schema requires) fails to deserialise into
`PluginCapabilities` immediately, with a `JsonException`:

```
$ dotnet run   # minimal repro: a class-typed property fed a JSON array, System.Text.Json 8
THREW JsonException: The JSON value could not be converted to Caps. Path: $.capabilities |
LineNumber: 2 | BytePositionInLine: 19.
```

`PluginManifestParser.Parse` (`src/NoMercy.Plugins/PluginManifestParser.cs:29`) does not
catch `JsonException` at all, so on the install path this propagates as an unhandled
exception. `nomercy-plugin verify`'s `ManifestScan.Run` does catch it
(`tools/nomercy-plugin/Verification/ManifestScan.cs:57-67`) and turns it into a `Blocked`
refusal:

```csharp
// ManifestScan.cs:57-67
catch (JsonException exception)
{
    return [ new PluginRefusal(
        PluginRefusalCodes.ManifestInvalid, folder,
        $"plugin.json could not be read: {exception.Message}",
        "A manifest that does not parse cannot be checked at all, so every other finding "
      + "below it would be a guess.",
        "Fix the JSON and run verify again. Docs: /nomercy-plugins/tour/manifest",
        PluginRefusalSeverity.Blocked) ];
}
```

— which tells the author to "fix the JSON," with no hint that the JSON they wrote is exactly
what the SDK's own published schema told them to write.

## Reproduction

1. Write a `plugin.json` whose `capabilities` field is an array of `{name, scope, reason}`
   objects, validating clean against `PluginManifestSchema.Json` (or the published schema at
   the same `$id`), and include an `entry` field per the schema's `required` list.
2. Run `nomercy-plugin verify` against it.
3. Observed: a `Blocked` `ManifestInvalid` refusal reporting a JSON conversion error on
   `$.capabilities`, saying to fix the JSON.
4. Expected: either the schema validates, or the refusal says the schema itself is wrong
   rather than blaming the author's JSON.

## What it costs

An author who trusts the generated, published schema over the working examples in this
workspace writes a manifest that cannot be read at all — not degraded, not partially
functional, refused outright, by the same tool whose schema produced the shape. `entry`
being both schema-required and runtime-unread is smaller but the same story in miniature: a
required field with nothing on the other end.

## Proposed fix (proposal, not decided)

Regenerate `PluginManifestSchema` from the actual `PluginManifest`/`PluginCapabilities`
shape (an object with `hooks`/`network`/`ui`/`rest`/`restAnonymous`/`ws`, not an array of
capability grants — that shape belongs to the runtime *grant* records
`ConfigPluginGrantStore` persists, a different concept with a similar name), and drop
`entry` from `required` until something reads it, or wire a real reader for it and keep the
requirement.
